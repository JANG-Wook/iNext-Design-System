# 토큰 설계 기록

**이 문서의 역할** — 토큰이 *무엇인지*는 JSON 의 `$description` 에 있다. 여기에는 **왜 그렇게 정했는지**, **무엇을 검토했다 버렸는지**, **아직 안 정해진 것**을 적는다. 작업 규칙은 `../CLAUDE.md` 에 있다.

최종 갱신: 2026-08-25

## 0. 스펙 기준

### 0-1. 기준 버전은 2025.10 이다

**Design Tokens Format Module 2025.10** · **Color Module 2025.10** — 둘 다 *Final Community Group Report, 2025-10-28* 이고 "considered stable" 로 표시돼 있다. 고정 릴리스를 근거로 쓴다.

- <https://www.designtokens.org/tr/2025.10/format/>
- <https://www.designtokens.org/tr/2025.10/color/>

`/tr/drafts/` 는 계속 움직이는 초안이라 근거로 쓰지 않는다. 내용이 지금은 같아도 버전을 특정할 수 없으면 준수 여부를 검사할 수 없다.

**그동안 버전이 명시되지 않았다.** `CLAUDE.md` 는 "DTCG 스펙으로 작성한다"고만 적었고, 그 결과 준수 주장이 검사 불가능한 문장이었다. 2026-08-25 에 버전을 박았다.

### 0-2. 왜 2025.10 인가 — 파일이 이미 거기에 있었다

2025.10 과 이전 형식(2nd Editors' Draft)은 값 형식이 **양립하지 않는다.** 우리 파일 실태를 두 버전에 대조하면 이렇다.

| 값 형식 | 건수 | 2nd Editors' Draft | 2025.10 |
|---|---:|:---:|:---:|
| `dimension` = `{value, unit}` 객체 | 82 | ✗ 문자열 `"16px"` 요구 | ✓ |
| `$type: "number"` | 40 | ✗ **number 타입이 없음** | ✓ |
| `shadow` 내부 offset/blur 객체 | 10 | ✗ | ✓ |
| `color` = hex 문자열 | 101 | ✓ | ✗ |
| `$type` 없음 | 32 | ✓ JSON 타입 폴백 | ✗ |

132건이 2025.10 전용, 133건이 2nd ED 전용이다. 즉 색 전환은 새 요구가 아니라 **파일 내부 불일치를 없애는 작업**이다.

**검토했다 버린 것**

| 안 | 왜 버렸나 |
|---|---|
| 2nd ED 를 기준으로 삼고 색 유지 | `dimension` 82건을 객체 → 문자열로 되돌려야 하고, 그 버전에 `number` 가 없어 `opacity` 26 · `interaction` 9 · `layout.columns` 5 가 **무타입 토큰으로 강등**된다. 후퇴이고 작업량도 더 크다. |
| `$extensions` 로 비표준 타입을 선언 | **유효성을 만들지 못한다.** 스펙은 타입을 결정할 수 없는 토큰을 도구가 무효로 취급해야 한다고 규정하고, 값에서 타입 추론도 금지한다. 확장 데이터를 붙여도 무효는 무효다. |

**색을 2025.10 으로 옮기는 부수 이득** — `colorSpace: "oklch"` 가 정식 지원된다. 우리 팔레트는 OKLCH 로 설계했는데 변환 결과인 hex 만 토큰에 남아 L·C·H 는 이 문서와 스크래치패드에만 있었다. 전환하면 설계값이 토큰 안으로 돌아온다. 단 복원되는 값은 **색역 매핑 후**라 클리핑 전 의도는 아니다 — 대신 실제 렌더링 값과 어긋나지 않는다.

**전환 시점을 지금으로 잡은 이유** — 패키지가 `private` 이고 외부 소비자가 0이다. 나중에 하면 제품 앱까지 같이 고쳐야 한다.

### 0-3. 스펙 밖의 값은 예외로 표시한다

`gradient.solid` · `multiple` 8건은 `currentColor` 를 쓴다. CSS 런타임 상속값이라 `colorSpace`+`components` 를 요구하는 DTCG `color` 로 표현할 방법이 없다. 즉 이 8개는 디자인 토큰이 아니라 **CSS 레시피**다.

`$extensions."net.infobank.ds.cssRecipe": true` 로 표시하고, 컴포넌트 단계에서 토큰 밖으로 옮길지 재검토한다. 예외는 늘리지 않는다.

> **갱신(2026-09-01):** 이 8건 중 절반이 나머지 절반의 중복이었다. `multiple` 4개를 제거하고 `solid` 을 `fade` 로 고쳐 **예외가 4건으로 줄었다**. 근거는 0-15.

### 0-4. 배포 형태 — `@infobank/next-ds-tokens`

2026-08-25, 저장소 루트에 `package.json` 을 만들었다. 그전에는 `CLAUDE.md` 가 5곳에서 `npm run build:tokens` 를 지시했지만 `package.json` 이 없어 실행되지 않았다.

| 필드 | 값 | 이유 |
|---|---|---|
| `name` | `@infobank/next-ds-tokens` | |
| `version` | `0.1.0` | 토큰 미확정 단계 |
| `private` | `true` | 실수 발행 방지. 공개 배포는 나중에 결정 |
| `type` | `module` | `tokens.js` 가 `export const` 21개. 없으면 Node 가 CJS로 읽어 전부 문법 오류 |
| `files` · `exports` | `tokens.css` · `tokens.js` 만 | 공개 API 를 산출물 2개로 한정. JSON 원본 · `build.mjs` · `preview.html` 은 배포 제외 |

의존성은 0을 유지한다 — `build.mjs` 가 Node 표준 모듈만 쓴다. lockfile · `node_modules` 를 만들지 않는다.

**소비자별 형식 변환은 어댑터로 한다.** JSON 을 단일 원본으로 두고 `build.mjs` 가 `tokens.css`·`tokens.js` 를 뽑는 구조가 이미 그것이다. Figma 등은 출력 대상이 하나 더 붙는 것이고, **특정 소비자의 형식이 원본 형식을 결정하게 두지 않는다.**

### 0-5. 원시 스케일은 한 곳에만 둔다

2026-08-25, `interaction.opacity.*` 9건이 숫자를 직접 들고 있었고 그중 7건이 `opacity` 그룹과 값이 같았다. 오버레이 강도를 조정할 때 두 곳을 봐야 하고 어느 쪽이 원본인지 알 수 없는 상태였다.

9건 전부를 `{opacity.N}` 별칭으로 바꿨다. 스케일 밖이던 0.09 · 0.18 은 `opacity.9` · `opacity.18` 로 흡수했다. 이를 위해 `build.mjs` 에 `deref()` 를 넣어 `number`·`dimension` 의 primitive 내부 별칭을 해석하게 했다 — 그전에는 미해석이라 별칭을 쓰면 CSS 에 `{opacity.5}` 가 문자열로 나갔다.

검증: `tokens.css` 가 신설 2줄 외에 **바이트 단위로 동일**했다.

### 0-6. 이주 1차 — `ratio` · `layout.maxWidth` · `gradient`

2026-08-25. `$type` 을 결정할 수 없던 32건을 처리했다.

| 대상 | 건수 | 처리 | 결과 |
|---|---:|---|---|
| `layout.maxWidth.xs·sm·md` | 3 | **토큰 삭제** | `"none"` 은 값이 아니라 값의 부재다. `dimension` 은 키워드를 허용하지 않으므로 "제약 없음"은 토큰을 두지 않는 것으로 표현한다. `maxWidth` 는 `lg`·`xl` 만 남았다. 컴포넌트는 `lg` 이상에서만 `max-width` 를 건다. |
| `ratio.*` | 21 | `$type: "number"` | 폭÷높이. CSS `aspect-ratio` 는 단일 숫자를 받는다. 비율의 의미는 키(`16-9`)가 담는다. |
| `gradient.solid`·`multiple` | 8 | `cssRecipe` 예외 표시 | `currentColor` 는 표현 불가 — 0-3 참조. **2026-09-01 에 중복 4건을 제거하고 `gradient.fade` 4건으로 줄였다(0-15).** |

**`ratio` 값 형식이 바뀐 대가** — CSS 출력이 `16 / 9` 에서 `1.777778` 로 바뀌어 가독성이 내려갔다. 소수 6자리로 반올림했고 1920px 폭에서 오차는 0.0001px 미만이다. 대안으로 폭·높이를 `number` 두 개로 쪼개 빌드가 `16 / 9` 를 조립하는 방법이 있었으나, 토큰이 21 → 42개로 늘고 JS 소비자가 값을 직접 조립해야 해서 버렸다.

**남은 무효 토큰은 색 101건 + `gradient` 8건이다** (작업 전 133건 → 109건). `gradient` 8건은 예외로 확정했으므로 실질 대상은 색 101건이다.

**부수 수정** — `preview.html` 의 `valueOf` 에도 별칭 해석이 없어 0-5 작업 직후 `interaction.opacity` 9건이 `{opacity.5}` 문자열로 표시되고 있었다. `resolveAliasTok()` 을 넣어 고쳤다(기존 `derefPrim(prim, ref)` 과 이름이 겹쳐 한 번 깨뜨렸다).

### 0-7. 이주 2차 — 색 101건을 oklch 객체로

2026-08-25. hex 문자열이던 primitive 색 101건을 2025.10 형식으로 바꿨다.

```json
"600": {
  "$type": "color",
  "$value": { "colorSpace": "oklch", "components": [0.545847, 0.210951, 260.1367], "hex": "#1266E8" }
}
```

**설계값이 토큰으로 돌아왔다.** 팔레트를 OKLCH 로 설계했는데 그동안 변환 결과인 hex 만 남아 L·C·H 는 이 문서와 스크래치패드에만 있었다. 이제 hue 정리(1-4)가 값으로 확인된다 — `yellow.400` H=100.4° · `teal.600` H=179.9°.

**변환은 무손실이다.** hex → OKLCH 는 결정론적 가역 변환이라 101건 전부 왕복이 정확히 일치했다(소수 L·C 6자리, H 4자리). 무채색 4건(`#FFFFFF`·`#000000` 등 r=g=b)은 색상이 정의되지 않으므로 C=0 · H=`"none"` 으로 뒀다 — 스펙이 허용하는 표기다.

**`hex` 필드는 원본 문자열을 그대로 유지했다.** 소문자로 정규화했더니 `tokens.css` 에 대소문자 차이만 있는 diff 가 101줄 생겼다. 값은 같지만 통과 조건을 "diff 없음"으로 잡았으므로 원본 대소문자를 보존했다.

**검증** — `tokens.css` · `tokens.js` 모두 **바이트 단위로 동일**. AA 대비 재검증 144건 미달 0.

#### 새 위험과 그 대응

한 색이 `components` 와 `hex` **두 표현**을 갖게 됐다. 하나만 고치면 소비자가 어느 쪽을 읽느냐에 따라 다른 색이 나온다. `build.mjs` 에 `assertColorHexMatchesComponents()` 를 넣어 매 빌드마다 막는다.

| 검사 | 내용 |
|---|---|
| 형식 | `{colorSpace, components, hex}` 를 갖췄는가 · `colorSpace` 가 `oklch` 인가 |
| 일관성 | `components` 를 sRGB 로 역변환한 값이 `hex` 와 같은가 |

두 시나리오로 시험했다 — ① `hex` 만 바꿈 → 빌드가 `components 와 hex 가 어긋난다` 로 실패 ② 둘을 함께 다른 색으로 바꿈 → `verify.mjs` 가 값 변경으로 실패. 어느 쪽도 조용히 통과하지 않는다.

**소비 지점** — `build.mjs`(2곳) · `preview.html`(4곳) · `verify.mjs` · `surfaces.mjs` 에 `hexOf()` 를 넣어 객체에서 hex 를 꺼내게 했다. `verify.mjs` 섹션 C(무채색 무회귀)는 원본 JSON 비교에서 **해석된 hex 비교**로 바꿨다 — 형식 변경은 허용하되 색 값 변경·삭제·추가는 여전히 잡는다.

**프리뷰** — primitive 색 칩에 oklch 성분 줄을 추가했다. hex 만 보이면 전환의 이득이 화면에 안 나타난다.

### 0-8. 정합성 감사와 이주 3차 — 타이포·자간·반경

2026-08-25. 스펙 원문(Format 91KB · Color)을 내려받아 조항만으로 검사기를 새로 작성하고 4개 JSON 을 전수 감사했다. **오류 50건**이 나왔고, 모두 이전부터 있던 것이었다.

| 조항 | 건수 | 처리 |
|---|---:|---|
| 9.8 typography 하위 타입 | 33 | `lineHeight` 를 `dimension`(rem) → `number`(배수)로 전환 |
| 9.8 typography 필수 속성 | 12 | `compact` 6건에 `fontFamily`·`fontWeight` 보충 |
| 8.2 dimension 단위 | 4 | `letterSpacing` `em` 유지 + 예외 표시 |
| 8.2 dimension 단위 | 1 | `radius.circle` `%` → CSS 문자열 + 예외 표시 |

**통과한 것** — 이름 규칙(`$` 시작·`{}`·`.` 금지) · `shadow` 5속성 · `color` 101건 · 별칭 154건 무결성 · `$extensions` 표기.

#### 행간을 배수로 바꾼 판단

스펙 9.8 은 `lineHeight` 를 **fontSize 배수인 `number`** 로 요구한다. 2-1 에서 세운 "2px 그리드를 원본으로" 는 절대값을 전제했으므로 정면 충돌이었다.

**전환을 택한 이유**

| | |
|---|---|
| 그리드는 렌더링에서 유지된다 | 배수 복원 오차 최대 **0.000008px**. 브라우저 레이아웃 격자(1/64px)보다 2000배 작다. 실제로 프리뷰에서 `body-md` 22px · `heading-md` 36px · `label-sm` 16px · `display-lg` 72px 로 확인했다 |
| CSS 상속이 옳아진다 | 3-1 에 기록한 rem 전환 시 상속 동작 변화가 원복된다. 무단위 행간이 CSS 정석이다 |
| 접근성 규칙과 단위가 맞는다 | `CLAUDE.md` 의 "본문 행간 ≥1.5" 가 배수 기준인데 토큰도 배수가 됐다 |

잃은 것은 "그리드에 정확히 떨어진다"는 **구성상 보장**이고, 화면상의 정렬이 아니다.

#### 이름을 `글자px-행간px` 로 한 이유

배수 값(`1.571429`)만으로는 2px 그리드에서 나왔다는 근거가 토큰에서 사라진다. 검토한 대안과 버린 이유는 이렇다.

| 안 | 버린 이유 |
|---|---|
| 역할 이름(`tight`/`normal`/…) | 배수가 **12종**이라 4~5개 티어로 못 담는다. 게다가 `16-24`와 `12-18`이 둘 다 1.5, `24-32`와 `12-16`이 둘 다 1.333333 이라 역할 이름은 **서로 독립인 결정을 하나로 합쳐버린다** |
| typography 에 배수 직접 기입 | 행간 하나를 2~3개 토큰이 공유한다(`body-md`·`body-md-strong`·`link-md`). 인라인하면 한 결정을 세 곳에서 고쳐야 하고 인라인 금지 규칙과도 충돌 |

토큰은 13개 → **14개**가 됐다. `lineHeight.26` 이 16px·18px 두 곳에 쓰여 `16-26`(1.625)·`18-26`(1.444444)로 갈라졌다.

**새 가드** — `assertLineHeightPairing()` 이 매 빌드에서 4가지를 검사한다: 키 형식 · `fontSize` 와의 짝 · `$type`=number · 배수↔px 복원. 세 시나리오로 고의 파손 시험을 했고 전부 실패로 잡혔다. 이름이 담은 "이 크기 전용"이라는 약속이 문서가 아니라 빌드로 강제된다.

#### `letterSpacing` 은 (이때는) 맞추지 않았다 — **2026-08-25 에 전환했다, 0-11 참조**

`em` 은 DTCG `dimension` 이 담지 못한다(px·rem 만). 그러나 자간은 **글자 크기에 비례해야** 하고, 밴드 하나가 여러 크기를 덮는다 — `heading` 은 24·28·32·36px 넷을 덮는다. `rem` 으로 바꾸면 4개가 **10개**로 늘고 밴드 구조가 사라진다. 스펙의 한계이지 우리 설계의 결함이 아니므로 `em` 을 유지하고 예외 표시했다.

`$type: "dimension"` 은 **남겨뒀다.** 빼면 typography 의 `letterSpacing` 참조가 무타입 토큰을 가리켜 위반이 4건에서 37건으로 번진다. 위반을 4건 안에 가두는 쪽을 택했다.

#### `compact` 은 토큰만 채우고 CSS 는 그대로

스펙은 소스 병합을 **토큰 단위 교체**로 정의한다(속성 단위 병합이 아니다). 그래서 `compact` 도 5속성을 다 갖춰야 한다. 다만 `build.mjs` 는 미디어쿼리에 `font-family`·`font-weight` 를 다시 쓰지 않는다(`full=false`) — **JSON 이 스펙을 지키고 빌드가 출력을 최적화**하는 것이 원본/산출물 분리에 맞다.

#### 남은 예외 13건

| 대상 | 건수 | 이유 |
|---|---:|---|
| `gradient.solid`·`multiple` | 8 | `currentColor` — 런타임 상속값. **2026-09-01 에 `gradient.fade` 4건으로 축소(0-15)** |
| `letterSpacing` | 4 | `em` — 글자 크기 상대 단위 |
| `radius.circle` | 1 | `%` |

**오류 0건 · 미표시 0건.** 셋 다 DTCG 타입 체계에 없는 CSS 개념이다.

#### 검토했으나 이번에 하지 않은 것 — Resolver Module

`compact` 을 자체 `$extensions` 로 옮기는 안을 검토하다가 **Resolver Module 2025.10** 을 확인했다. 도입부가 드는 예가 정확히 우리 두 경우다 — *Theming(light/dark)* 와 *Sizing(mobile/tablet/desktop)*. `sets`/`modifiers`/`contexts` 구조가 우리 파일 배치와 거의 1:1 이라, 도입하면 `semantic.light`↔`dark` 키 동기화나 `compact.X`↔`base.X` 이름 대응처럼 **지금은 아무것도 강제하지 않는 규약들이 규격으로 올라간다.**

미룬 이유는 **성숙도**다. Format·Color 는 *Final Community Group Report* 인데 Resolver 는 *Candidate Recommendation* 이다. "고정 릴리스만 근거로 쓴다"(0-1)의 예외를 만드는 일이라 별도 결정이 필요하다.

표준 경로가 있으므로 `$extensions` 로 자체 해결하지 않았다.

### 0-9. 파일 합성을 규격 개념으로 올리고 테마별 번들을 낸다

2026-08-25. 별칭 370건 중 **361건이 파일 경계를 넘는다**(semantic.light 98 · semantic.dark 98 · typography 165). 자기 파일 안에서 풀리는 건 `interaction.opacity` → `opacity` 9건뿐이다.

Format Module 의 별칭 해석은 **문서(파일) 단위**다 — 7.2.1 은 "Navigate to token"으로 문서 안을 탐색하고, JSON Pointer 의 `#/` 는 document root 다. 즉 `semantic.light.json` 만 읽는 도구에게 `{color.gray.900}` 은 해석 불가능한 참조다.

**단일 원본성 자체는 문제가 없었다.** 값은 primitive 리프에만 있고(인라인 0건) 산출물은 전부 생성물이다. 부족한 것은 **그 구조를 기계가 읽을 수 있게 선언한 것**이었다.

#### 한 것 — 개념 차용 + 번들

`build.mjs` 에 `COMPOSITION` 상수를 두고 파일 로딩·번들 생성을 여기서 구동한다.

```js
const COMPOSITION = {
  sets:      { base: ['primitive.json', 'typography.json'] },
  modifiers: { theme: { light: ['semantic.light.json'], dark: ['semantic.dark.json'] } },
  resolutionOrder: ['sets.base', 'modifiers.theme'],
}
```

그전에는 이 구성이 `prim`·`L`·`D`·`TYPO` 라는 **변수 이름에만** 있었다. "L 이 theme=light 컨텍스트"라는 사실이 코드 관례였다.

여기서 `dist/tokens.light.json` · `dist/tokens.dark.json` 을 낸다. 테마별 **단일 DTCG 2025.10 문서**로, 별칭 272건이 전부 문서 안에서 해석된다. 별칭을 값으로 풀지 않는다 — 참조 관계가 보존돼야 도구가 의미를 읽는다.

| | |
|---|---|
| 토큰 수 | 358개 = primitive 258 + typography 33 + semantic 67 |
| 키 충돌 | 없음 — `color` 는 primitive 15계열과 semantic 14그룹이 서로 겹치지 않는다 |
| 두 번들 차이 | 값이 다른 토큰 49개, 전부 semantic |
| 감사 | 오류 0 · 예외 26(13×2) |

**새 가드 2종** — `assertCompositionCoversSources()`(디스크 ↔ 등록 양방향) · `assertBundleSelfContained()`(번들 미해석 별칭 0건). 세 시나리오로 고의 파손 시험을 했고 전부 실패로 잡혔다.

#### Resolver 파일은 두지 않았다

| | |
|---|---|
| 성숙도 | Format·Color 는 *Final CG Report* 인데 Resolver 는 *Candidate Recommendation* 이다. 0-1 의 "고정 릴리스만 근거로 쓴다"의 예외가 된다 |
| 도구 지원 | Style Dictionary 도 Resolver 는 진행 중(🚧)이다. 파일을 둬도 오늘 읽는 도구가 없다 |
| **미루는 대가** | **없다.** 구성이 데이터로 있으므로 필요해지면 `COMPOSITION` 을 직렬화하면 된다 |

처음에는 resolver 파일을 손으로 관리하고 양방향 가드를 붙이는 안을 세웠으나, 구성을 데이터로 올리면 그 파일이 **생성 가능한 산출물**이 되므로 손으로 관리할 이유가 없다. 그 안은 버렸다.

#### 검토했다 버린 것 — 호환 번들

색을 hex 문자열, 크기를 `"16px"` 문자열로 낮춘 이전 형식 번들을 추가하는 안을 검토했다. 근거는 "오늘의 도구는 2025.10 객체 형식을 못 읽는다"였다.

**그 전제가 틀렸다.** [style-dictionary#1590](https://github.com/style-dictionary/style-dictionary/issues/1590) 확인 결과 **Color module · Dimension token types 는 이미 완료(✅)** 이고, 진행 중인 것은 Gradient · Duration · **Resolver** 다. 근거로 삼았던 penpot 이슈는 그 도구의 미구현이었을 뿐인데 도구 일반으로 일반화한 것이었다.

Figma 도 이유가 되지 않는다 — Figma Variables 는 자체 형식이라 어떤 형식으로 내보내도 플러그인 변환을 거친다. 형식을 낮춰도 어댑터는 그대로 필요하다.

버린 이유를 정리하면 이렇다.

| | |
|---|---|
| 전제 미검증 | 필요하다고 말한 소비자가 없다. 가정을 위해 짓는 일이었다 |
| 정보 손실 | 호환 번들에는 `hex` 만 남아 OKLCH 성분이 사라진다. 0-7 의 설계 근거가 그 산출물에서 소실된다 |
| 공식화 위험 | `exports` 에 올리면 소비자가 superseded 형식 위에 쌓고, 나중 마이그레이션을 우리가 떠안는다 |

**필요한 소비자가 실제로 나타나면 그때 빌드 타깃을 하나 더 만든다.** 그 시점엔 "누가 왜"가 분명해서 형식도 정확히 맞출 수 있다.

역설적으로 이 확인이 번들의 근거를 강화했다 — Style Dictionary 가 못 하는 것이 정확히 **Resolver(파일 합성)** 이고, 번들이 그 한 가지를 대신해 준다. 형식을 낮추는 게 아니라 형식은 정식으로 두고 합성만 미리 해서 넘기는 것이다.

#### `package.json` 공개 API

```
.            → tokens/tokens.js          (ESM export 21개)
./css        → tokens/tokens.css         (CSS 변수 224 + 클래스 33)
./dtcg/light → tokens/dist/tokens.light.json   ← 신설
./dtcg/dark  → tokens/dist/tokens.dark.json    ← 신설
```

배포 파일 5개, 210.9 kB. JSON 원본 · `build.mjs` · `preview.html` 은 여전히 제외한다.

### 0-10. 티어 스케일의 순서를 빌드가 지킨다 — `gradient.maskSize`

2026-08-25. 2-6 에서 미뤄둔 `gradient.maskSize` 이름 통일(`xsmall`~`xlarge` → `xs`~`xl`)을 하다가 **값이 이름 순서를 거스르고 있는 것**을 발견했다.

```
작업 전:  xsmall 24 · small 32 · medium 40 · xlarge 56 · large 64
                                              ↑ xlarge 가 large 보다 작다
```

JSON 기입 순서가 **이름 순서가 아니라 값 순서**(24·32·40·56·64)를 따르고 있었다. 값 간격은 8·8·**16**·8 로, 8단위 수열 `24 32 40 48 56 64` 에서 48이 빠진 모양이다.

**추정** — 원래 `xsmall/small/medium/large` = 24/32/40/64 네 단계였고, 나중에 56이 필요해져 **값 위치에 끼워 넣고 남은 이름 `xlarge` 를 붙인** 것으로 보인다. 단정할 수는 없다. git 이 없어 이력이 없고 이 문서에도 유래 기록이 없다.

#### 값을 지키고 이름을 고쳤다

```
xs 24 · sm 32 · md 40 · lg 56 · xl 64
```

**값 5개는 하나도 바꾸지 않았다.** 56과 64가 어느 이름에 붙는지만 오름차순으로 재배치했다.

**검토했다 버린 안** — 숫자 키(`maskSize.24 · 32 · …`)로 바꾸는 안을 한 번 적용했다가 되돌렸다. 근거로 "역할 기록이 없으니 티어 이름을 쓸 자격이 없다"를 들었는데, `xl > lg` 는 추측이 아니라 **티어 어휘의 정의**이므로 값을 지어내는 문제가 아니었다. 판단을 정정했다. 티어 이름 쪽이 `breakpoint`·`shadow`·`layout` 과 어휘가 통일된다.

#### 진짜 교훈 — 역할 기록이 없는 티어 스케일이 사고를 허용했다

꼬인 스케일이 하필 **DS 에서 유일하게 토큰별 `$description` 이 0인 티어 스케일**이었다.

| 스케일 | 키 | 토큰별 역할 기록 |
|---|---|---:|
| `breakpoint` | 티어 | 5/5 |
| `shadow`(semantic) | 티어 | 5/5 |
| `layout.*` | 티어 | 전부 있음 |
| **`gradient.maskSize`** | 티어 | **0/5** |

`breakpoint` 에 새 값을 끼우려면 "이건 태블릿 가로인가 데스크톱인가"를 정해야 해서 이름 충돌이 바로 드러난다. `maskSize` 는 정할 게 없어 아무 이름이나 붙여도 걸리지 않았다.

역할을 지어내 채우는 대신 **구조로 막았다.** `assertTierScalesOrdered()` 가 매 빌드에서 티어 스케일 6개의 값 순서를 검사한다. 복합 값(`shadow`)은 단일 수치가 없어 제외한다. 의도적 역순은 `TIER_EXEMPT` 에 이유와 함께 등록하고(현재 `layout.margin` 1건 — lg·xl 은 maxWidth 가 여백을 대신해 0), **예외가 더는 티어 스케일이 아니게 되면 그것도 실패**시켜 죽은 예외를 막는다.

시험 3종을 모두 통과했다 — 옛 상태 재현 · `breakpoint` 역전 · 죽은 예외.

#### 같은 유형을 전수 조사했다

스케일 58개를 5가지 흔적으로 훑었다(`anomaly.mjs`).

| 검사 | 결과 |
|---|---|
| ① 티어 이름 ↔ 값 순서 어긋남 | `layout.margin` 1건 — **의도**(`$description` 에 근거 있음), 가드에 예외 등록 |
| ② 기입 순서 ≠ 값 순서 | 4건 — 전부 **의도**(`fontWeight` 내림차순 · `lineHeight` 글자크기순 · `ratio` 가로/세로 구분) |
| ③ 규칙적 수열의 구멍 | `maskSize` 1건 — 48 누락 여부는 미확인 |
| ④ 티어 이름인데 역할 기록 0 | `maskSize` 1건 — 가드로 대체 보호 |
| ⑤ 같은 값을 가진 형제 | 10건 — 전부 **의도**(`lineHeight` 2쌍은 0-8 에 기록 · `layout` 은 "xs·sm 공통") |

**부수 발견 — `ratio` 에 같은 유형이 있다.** ②를 보다가 나왔다.

- `ratio.vertical` 4개(`1-1`·`3-4`·`2-3`·`1-2`)가 `ratio.horizontal` 안에 **키도 값도 동일하게** 또 있다. 21개 중 4개가 중복이라 고유 비율은 17개다.
- `ratio.horizontal` 이 **세로 비율 8개**(`4-5`·`3-4`·`2-3`·`10-16`·`golden-v`·`9-16`·`1-2`·`9-21`, 전부 값<1)를 담고 있다. 그룹 이름이 내용과 맞지 않는다.
- 여기도 `$description` 이 그룹 2개·토큰 21개 **전부 없다.** 같은 조건이 반복된다.

미결로 남긴다(§4). 미참조 토큰이라 소비자 영향은 없다.

**`anomaly.mjs` 의 한계** — 내림차순 정렬을 이상으로 잡고, 그룹 사이 중복은 잡지 못한다(`ratio` 중복은 ②의 부수 관찰로 나왔다).

### 0-11. 자간을 크기별 rem 으로 — 예외 4건 소멸

2026-08-25. 0-8 에서 "스펙이 표현하지 못하는 값"으로 남겨둔 `letterSpacing` 4건을 스펙 안으로 옮겼다.

#### 전환을 가능하게 한 두 가지 사실

**① 글자 크기 하나에 밴드가 하나뿐이다.** 실측하니 11개 크기가 각각 정확히 하나의 밴드에 대응했다 — 한 크기에 밴드가 둘 걸린 경우 **0건**.

```
12·14 → none        16·18·20 → title
24·28·32·36 → heading    40·60 → display
```

밴드가 "여러 크기를 하나로 덮는" 이득은 primitive 토큰 수에서만 났고, typography 쪽은 어차피 크기마다 다른 값이 필요했다.

**② `fontSize` 가 전부 `rem` 이라 `em` → `rem` 이 정확히 동등하다.** `em` 은 요소 글자 크기 상대, `rem` 은 루트 상대인데, 우리 글자 크기가 rem 이므로 둘이 같은 배율로 움직인다.

| 크기 | 밴드 | em | 계산 | rem |
|---:|---|---:|---|---:|
| 12·14 | none | 0 | — | 0 |
| 16 | title | −0.01 | ×1rem | −0.01 |
| 18 | title | −0.01 | ×1.125rem | −0.01125 |
| 20 | title | −0.01 | ×1.25rem | −0.0125 |
| 24 | heading | −0.015 | ×1.5rem | −0.0225 |
| 28 | heading | −0.015 | ×1.75rem | −0.02625 |
| 32 | heading | −0.015 | ×2rem | −0.03 |
| 36 | heading | −0.015 | ×2.25rem | −0.03375 |
| 40 | display | −0.02 | ×2.5rem | −0.05 |
| 60 | display | −0.02 | ×3.75rem | −0.075 |

**검증** — 33개 클래스의 계산된 자간 픽셀이 **오차 0으로 완전 일치**했다. `tokens.css` diff 는 letter-spacing 줄에만 걸렸다.

#### 설계 의도는 강화됐다

2-2 가 밴드를 만든 목적은 **"자간은 독립 축이 아니라 글자 크기의 종속 함수"** 를 표현하는 것이었다. 그런데 그 의도는 **문서에만 있고 강제되지 않았다** — `label-sm`(12px)에 `letterSpacing.display`(40px 이상용)를 물려도 빌드가 통과했다.

이제 키가 크기 자체(`letterSpacing.12` … `.60`)이고 `assertLetterSpacingPairing()` 이 검사한다.

| 검사 | 내용 |
|---|---|
| 키 ↔ fontSize | 짝이 어긋나면 실패 |
| 타입·단위 | `dimension` · `rem` 이 아니면 실패 |
| 파생 일치 | 값이 `trackingBands` 의 어느 밴드 × 크기로도 설명되지 않으면 실패 |
| 1:1 | 쓰이지 않는 자간 토큰이 남아 있으면 실패 |

시험 4종을 모두 통과했다. `lineHeight` 의 짝 검사(0-8)와 같은 형태라 두 하위 속성이 대칭이 됐다.

#### 대가

| | |
|---|---|
| 토큰 4 → **11개** | 크기를 추가하면 자간 토큰도 추가해야 한다. `lineHeight` 는 이미 그랬다 |
| 밴드 단위 수정 | `heading` 밴드를 조정하면 4개 토큰 + 확장을 함께 고쳐야 한다. 어긋난 상태로는 빌드가 통과하지 않는다 |
| 동작 차이 1건 | `.body-md` 를 적용한 뒤 **font-size 만 CSS 로 덮어쓰면** `em` 은 따라오지만 `rem` 은 따라오지 않는다. 권장하지 않는 패턴이다 |

#### 결과 — 참조가 있는 예외가 0이 됐다

| | 전 | 후 |
|---|---:|---:|
| 예외 총계 | 13 | **9** |
| 그중 **참조가 있는** 예외 | **4** | **0** |
| 번들 예외(13×2 → 9×2) | 26 | 18 |

남은 9건은 `gradient` 방향형 8 · `radius.circle` 1 이고 **참조가 0이라 무해**하다. 0-8 에서 제기한 "typography 33개로 번질 수 있다"는 연쇄 위험이 사라졌다 — 그 위험 자체는 스펙 명문이 아닌 추론이었지만, 불확실성을 없애는 값이 토큰 7개였다.

### 0-12. 불투명도 사다리 — 사실상 중복인 단계를 없앴다

2026-08-25. `opacity` 26개를 점검했다. 원래는 "눈금이 불규칙하다"고 판단했는데 **절대 간격으로 본 오류**였다. 알파는 상대 비율로 지각된다 — 4→5 는 +25%, 80→88 은 +10%. 비율로 재보면 사다리는 대체로 건강했다.


### 0-14. 상태 오버레이 — 강도만 있고 색이 없었다

`interaction.opacity.*` 9건은 **얼마나 얹을지**(0.05·0.08·0.12…)만 정의하고, **무엇을 얹을지**는 어디에도 없었다. 불투명도만으로는 렌더링할 수 없다. 토큰별 `$description` 도 0/9 였다 — `maskSize`·`ratio` 를 꼬이게 한 것과 같은 조건이다.

### 0-15. `gradient` — 절반이 중복이었다

2026-09-01. `interaction` 을 마치고 `gradient` 를 점검했다.

#### `solid` 과 `multiple` 은 같은 그라디언트였다

문자열이 달라 다른 토큰으로 보였지만, **방향과 stop 순서를 동시에 뒤집으면 같은 그림**이다.

```
solid.top       linear-gradient(to top,    transparent, currentColor)   위가 불투명
multiple.bottom linear-gradient(to bottom, currentColor, transparent)   위가 불투명   ← 같다
```

흰 바탕에 합성해 불투명하게 만든 뒤 `mix-blend-mode: difference` 로 겹쳐 확인했다. **네 쌍 모두 완전히 검게** 나왔다 — 픽셀 차이 0.

| | |
|---|---|
| `solid.top` | ≡ `multiple.bottom` |
| `solid.right` | ≡ `multiple.left` |
| `solid.bottom` | ≡ `multiple.top` |
| `solid.left` | ≡ `multiple.right` |

`ratio` 에서 `vertical` 4개가 `horizontal` 안에 그대로 또 있던 것과 같은 유형이다(0-13). 이름이 왜 안 맞았는지도 이걸로 설명된다 — `multiple` 은 여러 개가 아니라 **반대 방향 표기**였다.

**첫 실측은 틀렸다.** 반투명 레이어끼리 `difference` 로 겹쳤더니 검게 나오지 않아 "다르다"고 볼 뻔했다. 알파가 있는 레이어에는 difference 가 등가 검사로 성립하지 않는다 — 불투명하게 만든 뒤 비교해야 한다.

#### 이름 — `solid` → `fade`

`solid` 는 단색을 뜻하는데 단색이 아니다. 하는 일이 가장자리 페이드이므로 `fade` 로 바꿨다.

키 규약은 `solid` 쪽을 그대로 이어받았다 — **키 = 불투명한 가장자리 = 이 페이드를 놓는 자리**이며, CSS `to <방향>` 키워드와 일치한다. 값의 의미는 바뀌지 않았다.

#### `currentColor` 는 유지한다 — 예외지만 의도다

스펙 2025.10 에는 `gradient` 복합 타입(9.7 · `stops` + `angle`)이 있다. 우리 값 세 요소를 대조하면 `transparent` 는 alpha 0 인 color 로, 방향 4종은 `angle` 로 표현된다. **막는 것은 `currentColor` 하나뿐**이다.

그럼에도 유지한다. 쓰는 쪽이 `color` 에 면 색을 넣으면 **토큰 하나가 어느 면에서든 맞기** 때문이다. 특정 색을 박으면 그 면에서만 맞다.

```css
.card        { color: var(--color-bg-elevated); }
.card::after { background-image: var(--gradient-fade-bottom); }
```

`mask-image` 로 쓰면 알파만 읽혀 `currentColor` 가 무시된다. 실측했다 — 같은 마스크를 `currentColor`·`black`·`white` 로 만든 렌더 결과가 동일했다(`mask-mode: match-source` 는 그라디언트를 알파로 읽는다). 즉 **마스크 용도라면 예외를 없앨 수 있지만, 배경 페이드 용도에서는 `currentColor` 가 핵심 장치**다. 후자를 택했다.

#### 용도 정리 — 실무에 필요한 셋 중 하나만 갖고 있다

| | 용도 | 색 | 테마 | 현재 |
|---|---|---|---|---|
| A | **미디어 스크림** — 사진 위 어두운 층으로 글자 대비 확보 | 고정 검정 | 무관 | **없음** |
| B | **면 페이드** — 잘리는 콘텐츠를 면 색으로 덮음 | `currentColor` | 적응 | `gradient.fade` |
| C | **마스크 페이드** — 배경을 모를 때 가장자리를 녹임 | 무의미(알파만) | 무관 | 없음 (B 를 `mask-image` 에 써도 동작) |

A 는 접근성 요구가 붙는다. 사진은 픽셀마다 밝기가 달라 **최악의 경우(완전히 흰 사진)** 를 기준으로 눌러야 한다. 흰 글자 4.5:1 을 보장하는 임계값을 계산했다.

```
검정 스크림 alpha   흰 사진 위 합성색   흰 글자 대비
  0.48              #858585            3.71   ✘
  0.52              #7a7a7a            4.27   ✘   ← elevation.dim(라이트)로도 부족
  0.60              #666666            5.74   ✔   ← opacity 눈금에서 처음 통과
정확한 임계 alpha 0.5347
```

**A 는 지금 만들지 않는다.** 미디어 컴포넌트가 없어 참조 0인 토큰만 늘어난다. 착수할 때 위 계산을 근거로 만든다(미결 16).

#### `maskSize` 는 값을 건드리지 않았다

`24 · 32 · 40 · 56 · 64` 에서 **48만 결번**이고 이유 기록이 없다(미결 13 유지). 티어 이름이 `xs`~`xl` 5개뿐이라 48을 넣으면 6단계가 되어 어휘가 깨지고, 값을 재배치하려면 원 의도를 알아야 한다. `$description` 만 썼다.

#### 결과

| | 전 | 후 |
|---|---|---|
| `gradient` 토큰 | 13 | **9** |
| 토큰별 `$description` | 0/13 | **9/9** |
| DTCG 예외 (소스) | 9 | **5** (gradient 4 + `radius.circle` 1) |
| CSS 변수 | `--gradient-solid-*` · `--gradient-multiple-*` | `--gradient-fade-*` |

참조 0건이라 색·대비에 영향 없다. 그룹 `$description` 이 잘못 가리키던 참조(2-6 → 0-10)도 함께 고쳤다.

## 1. 색

### 1-1. 단계를 WCAG 상대휘도로 고정한다

유채색 13계열 × 6단계는 OKLCH 로 생성한다. 단계 번호는 **목표 상대휘도**로 정의하며, 계열이 달라도 같은 번호면 대비가 같다.

| 단계 | 목표 휘도 | 흰 배경 대비 | `#1A1B1C` 대비 | 역할 |
|---|---|---|---|---|
| 200 | 0.620 | 1.56~1.57 | 11.00~11.08 | 밝은 틴트 |
| 300 | 0.440 | 2.13~2.16 | 7.98~8.10 | 다크 텍스트(여유) |
| 400 | 0.278 | 3.17~3.23 | **5.33~5.44** | **다크 텍스트** · 라이트 비텍스트 |
| 500 | 0.200 | 4.16~4.24 | 4.06~4.14 | 균형점 |
| 600 | 0.156 | **5.07~5.13** | 3.36~3.40 | **라이트 텍스트** · 다크 비텍스트 |
| 700 | 0.098 | 7.02~7.14 | 2.42~2.46 | 라이트 텍스트(여유) |

**400 과 600 은 서로의 거울이다.** 라이트 테마는 600, 다크 테마는 400 을 쓰면 양쪽 모두 5.1~5.4 로 맞는다. `CLAUDE.md` 의 "라이트·다크 동등" 요구가 이 구조로 충족된다.

**왜 휘도 앵커인가.** 대비는 휘도의 함수다. OKLCH 의 L 을 고정하면 톤은 맞지만 대비는 계열마다 어긋난다. 반대로 휘도를 고정하면 대비가 정확히 맞고 L 편차는 5 이내로 따라온다(실측 400단계 63.1~68.0, 폭 4.9). 대비가 목적이므로 휘도를 앵커로 삼았다.

**검토했다 버린 것 — 동일 OKLCH L 고정.** 톤 균일도는 조금 낫지만 계열별 대비가 갈려서, 결국 토큰마다 대비를 따로 확인해야 한다. 자동 보장이라는 이점이 사라진다.

### 1-2. 채도 상한은 400~700 에만 건다

채도는 그 휘도·hue 에서 sRGB 가 허용하는 최대의 95% 를 쓰되, 400~700 에만 상한을 둔다(400 = 0.21, 500 = 0.22, 600 = 0.21, 700 = 0.18). **200·300 에는 상한이 없다.**

**왜 어두운 쪽만 막는가.** blue·violet·purple·pink 는 색역 특성상 어두워질수록 채도 여력이 커진다. 상한이 없으면 700 이 600 보다 더 채도가 높아져, "어두울수록 깊어진다"는 기대와 반대로 네온처럼 튄다. 상한이 실제로 구속하는 토큰은 15 개다 — `red.500~700`, `blue.600~700`, `violet.600~700`, `purple.400~700`, `pink.400~700`.

**200·300 의 상한은 한 번 걸었다가 풀었다.** 처음엔 밝은 단계를 균일한 파스텔로 만들려고 0.11 / 0.17 을 걸었는데, `yellow.200` 이 카키(`#DED078`), `green.200` 이 탁한 연두(`#9CDEA0`)가 되어 계열 정체성을 잃었다. 대비에는 아무 영향이 없는 제약이었으므로 해제했다. 해제로 8 개 토큰이 바뀌었고 대비는 그대로다.

> **주의** — 다음에 "일관성 있게 상한을 전부 풀자" 는 판단을 하지 말 것. 400~700 의 상한은 위 이유로 의도적으로 남긴 것이다.

### 1-3. 어두운 노랑·주황이 칙칙한 것은 색역 한계다

`yellow.400`(`#A29119`), `yellow.600`(`#7C6E11`), `orange` 전 단계는 **이미 그 휘도에서 가능한 최대 채도**다. 노랑은 본래 휘도가 높은 색이라, 라이트 테마 텍스트에 필요한 어두운 영역에서는 올리브가 될 수밖에 없다. sRGB 의 제약이며 조정으로 해결되지 않는다.

### 1-4. Hue 는 계열당 하나로 고정한다

| 계열 | hue | 계열 | hue | 계열 | hue |
|---|---|---|---|---|---|
| red | 26° | yellow | 100° | lightBlue | 240° |
| redOrange | 41° | lime | 122° | blue | 260° |
| orange | 61° | green | 146° | violet | 284° |
| | | teal | 180° | purple | 313° |
| | | cyan | 214° | pink | 335° |

기존에는 계열 안에서 hue 가 흔들렸다(blue 254~261°, violet 282~291°). 계열당 하나로 고정했다.

**lime 을 138° → 122° 로 옮겼다.** green(146°)과 8° 차이라 사실상 구분되지 않았다. 122° 로 옮겨 황록으로 분리했다. 이번 개편에서 인상이 가장 크게 바뀐 부분이다.

## 2. 타이포

### 2-1. 행간은 2px 그리드를 원본으로 둔다

> **갱신(2026-08-25):** 그리드는 여전히 설계 원본이지만 **저장 형태가 바뀌었다** — DTCG 9.8 요구에 따라 rem 절대값에서 fontSize 배수로 전환했다. 근거와 대가는 0-8 에 있다.

`primitive.lineHeight` 는 **키 = px, 값 = rem** 이다(`22` → `1.375rem`). 그리드는 13 종 — 16 · 18 · 20 · 22 · 24 · 26 · 28 · 32 · 36 · 40 · 44 · 52 · 72px. 전부 짝수다(4의 배수는 아니다).

**왜 배수(ratio)가 아닌가.** 이전에는 복합 토큰에 `1.5714` 같은 배수가 직접 적혀 있었다. 확인해 보니 27 개 전부 `목표 행간 px ÷ 글자 px` 로 정수가 떨어졌다 — 즉 진짜 원본은 px 그리드였고 파일에는 계산 결과만 남아 있었다. 배수는 글자 크기에 종속돼 재사용이 불가능하다(같은 24px 행간이 16px 글자에선 1.5, 20px 글자에선 1.2). 그래서 배수를 primitive 로 올리면 `lineHeight.1-5714` 같은 무의미한 이름이 된다. 그리드를 원본으로 두는 쪽을 택했다.

**rem 을 쓴 이유.** 절대 px 로 두면 사용자 글자 확대에 반응하지 않는다. rem 이면 글자와 행간이 같은 비율로 커진다. 전환 후 33 개 유틸 클래스가 픽셀 단위로 이전과 동일함을 확인했다.

**검토했다 버린 것 — 빌드에서 `행간px ÷ 글자px` 계산.** rem 으로 두면 나눗셈이 필요 없고 `build.mjs` 는 `fontSize` 와 동일한 별칭 변환만 추가하면 된다. 더 간단해서 이쪽을 택했다.

### 2-2. 자간은 크기 밴드 4개다

> **갱신(2026-08-25):** 밴드라는 **설계 의도는 그대로**이고 **저장 형태만 바뀌었다** — 밴드 4개(`em`)에서 크기별 11개(`rem`)로. 밴드 원본은 `$extensions."net.infobank.ds.trackingBands"` 에 남아 있고, "자간은 크기가 결정한다"를 이제 빌드가 강제한다. 근거는 0-11 에 있다.

| 토큰 | 값 | 적용 글자 크기 |
|---|---|---|
| `letterSpacing.display` | `-0.02em` | 40px 이상 |
| `letterSpacing.heading` | `-0.015em` | 24~36px |
| `letterSpacing.title` | `-0.01em` | 16~20px |
| `letterSpacing.none` | `0em` | 14px 이하 |

자간은 독립 축이 아니라 **글자 크기의 종속 함수**다. 실측 결과 같은 크기인데 자간이 다른 경우가 한 건도 없었다. 원래 `typography.json` 의 설명에도 "자간 = 크기밴드 파생값" 이라고 적혀 있었고, 그 의도대로 밴드를 토큰화했다.

### 2-4. `spacing` 에서 홀수·반픽셀 4개를 제거했다

`0.5` · `3` · `5` · `7` 을 지웠다(19 → 15개). 1~8 구간이 1px 단위로 8단계나 있었는데 실무에서 `2·4·6·8` 만 쓰이고 홀수는 거의 쓰이지 않는다. 남은 스케일은 전부 짝수이며, 4px 그리드(`4·8·12·16·20·24·32·40·48·56`)에 미세 조정용 `1·2·6·10·14` 가 붙는 구조다.

`0.5px` 는 헤어라인용으로 추정됐으나 배율 1x 화면에서 0 또는 1px 로 반올림돼 의도대로 나오지 않고, 같은 용도로 `divider.1`(1px) 이 이미 있다. 삭제 직전 참조 0 건을 확인했다.

### 2-5. `radius` 는 사용처를 토큰에 적었다

`spacing` 과 달리 `radius` 는 각 단계의 사용처가 정해져 있어 `$description` 에 기입했다(0 · 4 · 6 · 8 · 12 · 16 · 20 · circle · full). `radius.0` 을 새로 추가했다 — `CLAUDE.md` 상 `0` 은 구조적 상수로 하드코딩 예외이지만, 스케일을 0 부터 완결시키고 "모서리 없음"을 명시적으로 표현하기 위해 토큰으로 뒀다.

`12`(카드·팝업)와 `20`(더 큰 컨테이너)의 경계는 원 설명에서 둘 다 "카드"를 가리켜 모호했다. **12 를 개별 카드·팝업, 20 을 그보다 큰 컨테이너로 해석해 적었다** — 실제 의도와 다르면 조정이 필요하다.

### 2-3. 레거시 51개를 제거했다

이전 세대의 px 기반 토큰 — `fontSize` 16 개(`display-1` 등), `lineHeight` 19 개, `letterSpacing` 16 개. 참조가 0 건이었고, px 라 글자 확대에 반응하지 않았으며, `tokens.css` 에는 그대로 출력되고 있어 신·구를 혼동할 위험이 있었다. 삭제 직전 참조 0 건을 재확인하고 제거했다.

## 2-6. Elevation — 5단계로 축소, 약어 통일, semantic 이동

`shadow` 11개 중 **6개를 삭제**했다 — `spread.small` · `spread.medium` · `segmentKnob` · `switchIosKnob` · `textOverlay` · `pageIndicatorText`. 넷은 컴포넌트 전용 이름인데 해당 컴포넌트가 없고, `$description` 도 참조도 없어 용도를 확인할 수 없었다. `spread` 2개는 blur 60·75px 로 그림자보다 광원에 가까웠으나 역시 근거가 없었다. 필요해지면 컴포넌트 구현 시 값을 새로 정한다.

남은 5개는 `normal.` 중간 단계를 없애고 이름을 바꿨다. **값은 그대로다.**

| 이전 | 이후 | CSS 변수 |
|---|---|---|
| `shadow.normal.xsmall` | `shadow.xs` | `--shadow-xs` |
| `shadow.normal.small` | `shadow.sm` | `--shadow-sm` |
| `shadow.normal.medium` | `shadow.md` | `--shadow-md` |
| `shadow.normal.large` | `shadow.lg` | `--shadow-lg` |
| `shadow.normal.xlarge` | `shadow.xl` | `--shadow-xl` |

**이름 규칙의 근거.** 이 DS 의 숫자 키는 전부 "숫자 = 실제 값"이다(`spacing.16`=16px, `radius.8`=8px, `lineHeight.22`=22px, `opacity.52`=52%). 그림자는 `x·y·blur·spread·color` 가 묶인 복합 토큰이라 단일 숫자로 표현할 수 없으므로, `shadow.1/2/3` 같은 서수를 쓰면 숫자 키의 의미가 깨진다. 같은 복합 토큰인 `typography` 가 이미 t-shirt 약어(`-xl`/`-lg`/`-md`/`-sm`)를 쓰고 있어 그쪽에 맞췄다.

> **원칙** — 판별 기준은 "값이 바뀌어도 이름이 여전히 맞는가" 다.
> - **이름이 값 자체인 것 → 숫자.** `spacing.16`(16px) · `radius.8` · `lineHeight.22` · `divider.1` · `opacity.52`. 값을 바꾸려면 다른 토큰을 쓰는 것이므로 이름과 값이 붙어 있어도 된다.
> - **이름이 역할·단계인 것 → 이름.** `shadow.md` · `typography.body-md` · `letterSpacing.heading` · `breakpoint.md`. 임계값·구성이 조정돼도 단계는 그대로 유효해야 하므로 값을 이름에 넣지 않는다.
>
> **티어 이름을 쓰면 값이 이름 순서를 따라야 한다.** `xl < lg` 같은 상태는 어느 명명 철학에서도 깨진 것이다. 빌드의 `assertTierScalesOrdered()` 가 강제하고, 의도적 역순은 `TIER_EXEMPT` 에 이유와 함께 등록한다.

**`gradient.maskSize`(5개)는 2026-08-25 에 `xs`~`xl` 로 바꿨다.** 그 과정에서 값이 이름 순서를 거스르고 있던 것이 드러났다 — 0-10 참조.

### Elevation 은 파일에서 두 곳, 문서에서 한 묶음이다

파운데이션 분류상 Elevation = **그림자 + dim** 이지만, 파일에는 `elevation` 이라는 단일 컨테이너가 없다.

```
semantic.light/dark.json
├── color
│   └── elevation
│       └── dim        $type: color   → --color-elevation-dim
└── shadow             $type: shadow  → --shadow-xs … --shadow-xl
```

**`$type` 이 다르기 때문이다.** dim 은 `background` 에 쓰는 색이고 그림자는 `box-shadow` 다. 한 그룹에 넣으면 빌드가 타입별로 분기해야 하고 CSS 변수 접두사도 성격이 다른 것이 섞인다.

**검토했다 버린 것 — `shadow` 그룹을 `elevation` 으로 개명.** 그러면 `--elevation-xs` 와 `--color-elevation-dim` 으로 접두사가 갈라져 오히려 헷갈린다.

**대신 문서와 미리보기에서 묶는다.** `preview.html` 에 **Elevation 섹션**을 두고 그림자 5개와 dim 을 함께 보여준다(dim 은 색 Semantic 섹션에서 제외해 중복을 막았다). 파운데이션 분류는 원래 문서상의 묶음이지 파일 구조와 1:1 일 필요가 없다 — Typography 도 `typography.json` + primitive 의 font 계열 5개 그룹에 걸쳐 있다.

### Divider — 숫자 키로 바꾸고 8px 로 줄였다

| 이전 | 이후 |
|---|---|
| `divider.thickness.normal` = 1px → `--divider-thickness-normal` | `divider.1` = 1px → `--divider-1` |
| `divider.thickness.thick` = **12px** → `--divider-thickness-thick` | `divider.8` = **8px** → `--divider-8` |

**t-shirt(`sm`/`lg`)가 아니라 숫자다.** divider 는 단순 치수라 `spacing.16`·`radius.8`·`lineHeight.22` 와 같은 계열이고, 위의 원칙(단일 수치 = 숫자, 복합 = t-shirt)을 그대로 적용했다. t-shirt 는 `shadow`·`typography` 처럼 여러 속성이 묶인 복합 토큰에만 쓴다.

`thickness` 중간 단계도 없앴다 — divider 가 두께만 정의하므로 구분할 대상이 없다(`shadow.normal.*` 을 없앤 것과 같은 이유).

12px 은 선이라기보다 띠로 보여 **8px** 로 줄였다. 참조가 `preview.html` 10곳뿐이라 함께 갱신했다.

**색은 이 토큰에 없다.** `$description` 에 명시했다 — 색은 `color.line.*` 에서 가져온다. 이전에는 이 사실이 어디에도 적혀 있지 않아, 미리보기가 `spacing` 과 같은 파란 막대로 그리는 바람에 "구분선이 파랗다"는 오해를 만들었다. 지금은 실제 `line.solidNormal` 색으로 그린다.

> `divider.8` 은 굵은 띠라서 실제로는 `line` 색보다 면 색(`bg.normalAlternative` 등)이 자연스럽다. 토큰 설명에 적어 뒀다.

### Dim 은 semantic 색이다

`color.material.dimmer` → **`color.elevation.dim`** 으로 개명했다(`--color-elevation-dim`). `material` 그룹은 사라졌다. 값·알파는 그대로다(라이트 `gray.910 @52`, 다크 `gray.900 @74`).

### 그림자 값 — 참조 스펙과 기존 값을 섞었다

기존 5개도, 참고로 받은 3개(새도우1·2·3)도 **그대로 쓰지 않고 양쪽에서 취해 새로 정의했다.**

| 출처 | 가져온 것 |
|---|---|
| 참조 스펙 | 방향 + 앰비언트 **2레이어 구조**, 앰비언트는 `0 0 y 0`(오프셋 없음), `blur/y` 비율이 깊어질수록 감소 |
| 기존 토큰 | 방향 레이어의 **음수 spread** — 그림자가 요소에 밀착해 붕 뜬 halo 를 막는다. 위쪽으로 더 넓은 범위 |
| 새로 정한 것 | 알파를 **단조 증가 램프**로(양쪽 다 아님). 앰비언트 알파도 단계별로 올린다 |

| 단계 | 방향 레이어 | 앰비언트 | 라이트 α | 다크 α | blur/y |
|---|---|---|---|---|---|
| `xs` | `0 1 3 0` | `0 0 1 0` | 0.08 / 0.04 | 0.48 / 0.24 | 3.00 |
| `sm` | `0 3 7 -1` | `0 0 3 0` | 0.12 / 0.05 | 0.70 / 0.30 | 2.33 |
| `md` | `0 6 14 -2` | `0 0 6 0` | 0.16 / 0.06 | 0.80 / 0.36 | 2.33 |
| `lg` | `0 12 24 -4` | `0 0 12 0` | 0.20 / 0.07 | 0.88 / 0.42 | 2.00 |
| `xl` | `0 20 36 -7` | `0 0 20 0` | 0.24 / 0.08 | 0.88 / 0.52 | 1.80 |

**y 램프를 `1·3·6·12·20` 으로 잡았다.** 참조 스펙의 `2·4·8` 과도, 기존의 `1·4·10·16·24` 와도 겹치지 않는다 — 어느 한쪽을 베낀 값이 아님을 구조적으로 보장한다.

**base 색은 `{color.gray.925}`(`#131314`).** 참조 스펙의 `rgb(20,20,20)` 에 가장 가까운 팔레트 값이며 채널 최대 차이가 1, 흰 배경 α0.2 에서 차이 0.2 로 보이지 않는다.

**다크는 깊은 단계일수록 라이트를 못 따라간다.** 알파를 88% 까지 올려도 `lg`·`xl` 은 48%·40% 수준이다(라이트 Δ47·57 을 내려면 알파 >1 필요). 얕은 단계는 64~66% 를 달성한다. `lg` 와 `xl` 의 방향 알파가 같은 88% 인 것도 이 상한 때문이며, 둘은 기하(y 12 vs 20)와 앰비언트 알파(42% vs 52%)로 구분된다.

### 그림자를 primitive 에서 semantic 으로 옮겼다

처음에는 `primitive.shadow` 에 두고 "테마 무관"으로 관리했으나 **두 가지 문제가 있었다.**

**① 다크에서 그림자가 보이지 않았다.** 그림자 색이 `rgba(23,23,23,…)` 인데 다크 배경이 `#1A1B1C`(= `rgb(26,27,28)`) 라 거의 같은 색이었다. 배경 위에 합성했을 때 채널당 변화가 라이트는 14~28, **다크는 0.2~0.4** 였다 — 8비트에서 반올림되면 사라지는 수준. 표면 밝기로 대체되지도 않았다(`bg.elevated` vs `bg.normal` 이 다크에서 1.07:1, 라이트에서는 아예 같은 값).

**② 색이 별칭이 아니었다.** `rgba(23,23,23,0.10)` 을 직접 기입해 "반투명색은 base 색 참조 + alpha(opacity 참조)" 규칙과 어긋났다.

그래서 `primitive.shadow` 를 제거하고 **`semantic.light/dark` 의 `shadow` 그룹**으로 옮겼다.

| | 라이트 | 다크 |
|---|---|---|
| base 색 | `{color.gray.900}` | `{color.gray.1000}` (순수 검정) |
| 알파 | 위 표 참조 | 위 표 참조 (상한 88%) |
| 기하 | 동일 (offset·blur·spread) | 동일 |

**base 색 치환은 무해하다.** 기존 `rgb(23,23,23)` 은 팔레트에 없는 값이었고, 가장 가까운 `gray.900`(`#161617`) 으로 바꿨을 때 흰 배경에서의 차이가 최대 0.12 — 보이지 않는다.

**다크는 라이트와 같은 강도를 낼 수 없다.** 배경이 이미 어두워 어둡게 만들 여지가 없다. 물리적 한계이며, 더 나은 다크 elevation 은 `bg.elevated` 를 밝게 하는 쪽으로 해결해야 한다(미결 11번).

**알파는 레이어별로 다를 수 있다.** `$extensions."net.infobank.ds.alpha"` 가 문자열이면 전 레이어 공통, 배열이면 레이어별로 적용된다(`xl` 이 `[12%, 10%]` 로 다르다).

**기하는 두 파일에 중복 기입되므로 빌드가 검사한다.** `build.mjs` 의 `assertShadowGeometryMatches()` 가 라이트/다크 기하 불일치와 알파 개수 불일치를 발견하면 빌드를 실패시킨다.

`opacity` 는 24단계가 됐다 — 원본 14단계는 값이 그대로이고 그림자용으로 `4 · 6 · 7 · 20 · 24 · 30 · 36 · 42 · 48 · 80` 을 추가했다. 중간에 추가했다가 값 변경으로 쓰이지 않게 된 `10 · 72` 는 제거했다. 현재 미참조 단계는 없다.

## 2-7. Breakpoint 를 `web` 에서 분리했다

파운데이션에서 Breakpoint 를 독립 항목으로 관리하기로 해 `web.breakpoint.*` → **`breakpoint.*`**(최상위)로 옮겼다. `build.mjs` 가 `web` 래퍼를 평탄화하고 있었으므로 **CSS 변수는 `--breakpoint-*` 그대로이고 산출물의 값·집합이 바뀌지 않았다**(선언 순서만 이동). `tokens.js` 에는 `breakpoint` export 가 새로 생기고 `web` 에서 빠졌다.

**5단계·현재 값을 유지했다.**

| 단계 | 값 | 뜻 |
|---|---|---|
| `xs` | 0px | 기준점 없음. 모바일 우선 설계의 기본 구간 |
| `sm` | 768px | 태블릿 세로 / 작은 화면 진입점 |
| `md` | 992px | 태블릿 가로 / 작은 데스크톱 |
| `lg` | 1200px | 데스크톱 |
| `xl` | 1600px | 와이드 데스크톱 |

**타이포 `compact` 오버라이드가 `breakpoint.sm`(768px)과 맞물린다.** `@media (max-width: 767.98px)` 로 동작하므로 `sm` 미만 구간이다. 두 값은 함께 움직여야 한다 — 한쪽만 바꾸면 어긋난다.

**t-shirt 이름을 쓴 이유.** breakpoint 는 **단계(tier)** 를 가리키고 px 는 그 임계값이다. `breakpoint.768` 로 두면 임계값을 792 로 조정하는 순간 이름이 거짓이 되고 모든 소비자를 고쳐야 한다. 반면 `spacing.16` 은 값을 바꾸는 게 아니라 다른 토큰(`spacing.20`)을 쓰는 것이므로 숫자가 맞다. 위의 다듬은 원칙이 이 차이를 담는다.

**`$value` 는 객체 형식을 유지했다.** 참고로 받은 샘플은 `"$value": "640px"`(문자열, DTCG 초기 드래프트)였으나, 이 프로젝트는 `{"value": 768, "unit": "px"}`(객체, 최신 스펙)를 dimension 토큰 전체에서 쓴다. breakpoint 만 문자열로 바꾸면 `build.mjs` 의 `valueOf` 가 깨지고 100개 넘는 다른 dimension 토큰과 형식이 갈린다.

**`web` 에 남은 것** — `screen`(4) · `container`(2) · `layout`(1). 이 7개가 Artboard·Layout 파운데이션으로 갈 후보다.

## 2-8. Layout — 그리드를 breakpoint 단계별로 정의했다

`web.container`(2) · `web.layout`(1) 3개를 걷어내고 최상위 **`layout`** 을 신설했다. **4속성 × 5단계 = 20개**이며 키가 `breakpoint` 와 1:1 대응한다.

| 단계 | maxWidth | columns | margin | gutter |
|---|---|---|---|---|
| `xs` · `sm` | `none` | 4 | 20px | 12px |
| `md` | `none` | 8 | 20px | 16px |
| `lg` · `xl` | **1080px** | 12 | 0 | 24px |

**`"auto"` 를 `none` 으로 표현했다.** 최대폭 제약이 없다는 뜻이고, CSS `max-width` 의 초기값이 `none` 이라 그대로 쓸 수 있다(`auto` 는 `max-width` 에 유효하지 않다). `$type` 은 두지 않았다 — `ratio`·`gradient` 처럼 값 자체가 문자열인 경우와 같은 방식이다.

**`margin: 0` 은 여백이 없다는 뜻이 아니다.** `lg`·`xl` 에서는 `maxWidth`(1080px)가 여백을 만든다 — `lg`(1200)에서 좌우 각 60px, `xl`(1600)에서 각 260px. 이 관계를 `$description` 에 적었다.

**산수를 검증했다** — 전 단계에서 컬럼 폭이 양수다.

| 단계 | 컨텐츠 폭 | 거터 합 | 컬럼 폭 |
|---|---|---|---|
| `xs`(375 가정) | 335 | 36 | 74.8 |
| `sm`(768) | 728 | 36 | 173.0 |
| `md`(992) | 952 | 112 | 105.0 |
| `lg`·`xl` | 1080 | 264 | 68.0 |

### 교체된 옛 값

| 제거 | 대체 |
|---|---|
| `web.container.maxWidth` = **1100px** | `layout.maxWidth.lg`·`.xl` = **1080px** |
| `web.container.maxWidthXl` = **1440px** | 없음 — `xl` 도 1080px |
| `web.layout.paddingHorizontal` = 20px | `layout.margin.*` (단계별) |

**1100 → 1080, 1440 → 1080 으로 값이 바뀌었다.** 참조가 0건이어서 안전했다(`preview.html` 도 이 변수를 쓰지 않았다).

### margin·gutter 가 spacing 과 값이 같은 것은 의도된 독립이다

`layout.margin.xs`(20px) ↔ `spacing.20`, `layout.gutter.md`(16px) ↔ `spacing.16` 등 8건이 같은 숫자를 갖는다. **묶지 않는다.**

**① 두 축은 다른 이유로 바뀐다.** `spacing` 은 컴포넌트 내부 여백(버튼 패딩, 리스트 간격), `layout` 은 페이지 그리드(뷰포트 여백, 컬럼 사이)다. "카드 안쪽 여백을 16→20" 이라는 변경이 그리드 거터를 끌고 가면 안 된다.

**② 숫자 키 스케일에서 별칭은 유지보수 이득이 없다.** 색은 `gray.900` 의 hex 를 조정하면 참조가 전부 따라오므로 별칭이 실질 이득이다. 반면 `spacing.16` 은 정의상 항상 16px 이라(키가 곧 값) 거터를 20px 로 바꾸는 일은 별칭을 `{spacing.20}` 으로 고치든 raw 값을 고치든 작업량이 같다.

**③ 드리프트 위험이 없다.** `spacing.16` 이 미래에 다른 값이 될 방법이 없으므로 두 값이 어긋날 수 없다.

**업계 경향도 그리드가 자기 값을 갖는 쪽이 흔하다** — Material 3 는 window size class 별 margin·gutter 를 그리드 스펙에서 직접 정의하고, Carbon 도 거터를 그리드가 소유한다. Tailwind 는 반대로 `gap` 이 spacing 스케일을 공유하지만 유틸리티 기반이라 축을 나누지 않는 구조다. (각 시스템 내부 구현까지 확인한 것은 아니며 일반적 경향 수준의 근거다.)

> **주의** — "중복이니 별칭으로 묶자" 는 판단을 하지 말 것. 단, 그리드 값은 4px 그리드와 `spacing` 스케일 위에 두는 관례를 지킨다(현재 `0 · 12 · 16 · 20 · 24` 전부 해당, 스케일 밖 값 0건).

별칭의 유일한 실익은 "그리드 값이 스케일 위에 있음을 강제" 하는 것인데, 이미 지켜지고 있어 `build.mjs` 수정 비용을 들일 이유가 없다.

**`web` 에 남은 것** — `screen`(4)뿐. Artboard 파운데이션의 재료다.

## 2-9. Artboard 는 디자인 토큰으로 두지 않는다

`web.screen` 4개(`desktop` 1440×960, `mobile` 375×635)를 **삭제했다.** `web` 그룹은 이것이 마지막 항목이어서 함께 사라졌다.

**설계 캔버스는 토큰이 아니다.** 디자인 토큰은 코드가 읽어 화면을 그리는 값인데, 이 4개는 그렇지 않았다.

| 근거 | 확인 내용 |
|---|---|
| 제품이 소비하지 않음 | JSON 별칭 0건 · `preview.html` `var()` 0건. 그런데 CSS 에는 4개가 노출돼 있었다 |
| 높이는 웹에서 쓸 수 없음 | 반응형 레이아웃에 고정 높이는 없다. 뷰포트 높이는 사용자가 정한다 |
| 실기기 값이 아님 | `375×635` 의 635 는 어느 기기와도 안 맞는다(SE2 667, X 812). `1440×960` 의 960 도 임의 높이 — Figma 프레임 값이다 |
| **실제 오용 흔적** | 제거된 옛 `container.maxWidthXl` 이 **1440px** = `screen.desktop.width` 와 동일했다. **설계 폭을 컨텐츠 최대폭으로 착각한 것**으로 보인다. 실제 컨텐츠 최대폭은 `layout.maxWidth` = 1080px 다 |

마지막 항목이 결정적이었다 — `--screen-desktop-width` 가 CSS 에 있으면 `max-width: var(--screen-desktop-width)` 로 잘못 쓰기 쉽다. **토큰으로 노출하는 것 자체가 위험**이었다.

### 설계 기준 캔버스 (기록용)

값 자체는 팀 합의로서 의미가 있으므로 여기에 남긴다. **코드에서 참조하지 말 것.**

| | 폭 × 높이 |
|---|---|
| 데스크톱 | 1440 × 960 |
| 모바일 | 375 × 635 |

> `635` 와 `960` 의 출처는 확인되지 않았다. 특정 기기나 사내 규격이 근거라면 이 판단을 재검토할 수 있다.

**검토했다 버린 것 — JSON 에 남기고 CSS 출력만 제외.** `$extensions` 로 design-time 표시를 하고 빌드가 걸러내는 방식이다. Figma 플러그인이나 시각 회귀 테스트 뷰포트로 쓸 수 있다는 이점이 있으나, **지금 이 값을 소비하는 도구가 하나도 없어 가정에 불과하다.** 필요해지면 그때 되돌리는 편이 싸다.

### 부수 정리

`web` 그룹이 없어져 `build.mjs` 의 `cssVar()` 에서 **web 래퍼 평탄화 로직을 제거**했다(`pathArr[0] === 'web' ? …`). `breakpoint`·`layout` 은 이미 최상위로 승격돼 있었으므로 CSS 변수·값 집합은 바뀌지 않았다.

## 3. 소비자 주의사항

### 3-1. 행간 상속 동작이 바뀌었다

배수(`1.5714`) → 절대값(`1.375rem`) 으로 바뀌면서 **상속 동작이 달라졌다.**

- 요소마다 유틸 클래스를 직접 붙이는 경우 — 영향 없음
- 컨테이너에 클래스를 걸고 자식이 **다른 글자 크기**를 갖는 경우 — 행간이 자식 크기에 비례하지 않고 절대값 그대로 상속된다

컴포넌트를 "컨테이너에 걸고 상속" 패턴으로 설계할 계획이라면 이 결정을 재검토해야 한다.

### 3-2. 색은 라이트 600 / 다크 400

새 컴포넌트에서 유채색 텍스트가 필요하면 반드시 semantic 을 쓴다. primitive 를 직접 참조해야 하는 경우에도 라이트는 600, 다크는 400 규칙을 지킨다.

### 3-3. 미사용 단계

semantic 이 참조하는 것은 400 과 600 뿐이다. 200 · 300 · 500 · 700 은 현재 미참조지만 **완전한 스케일을 갖추기 위해 의도적으로 유지**한다. 미사용이라는 이유로 지우지 말 것.

## 4-1. 접근성 기준 — 무엇을 근거로 삼는가

`CLAUDE.md` 가 요구하는 **WCAG 2.2 AA + KWCAG 2.2** 의 실제 조항을 확인했다(2026-08-24).

### KWCAG 2.2 (33개 검사항목 / 14지침 / 4원칙)

| 항목 | 내용 |
|---|---|
| **5.4.3 텍스트 콘텐츠의 명도 대비** | 텍스트와 배경 간 **4.5:1 이상**. 예외 — 로고, 장식 목적 콘텐츠, 초점 시 대비가 커지는 콘텐츠. **큰 텍스트 예외 — 18pt 이상 또는 14pt 굵은 폰트면 3:1 까지 낮출 수 있다** |
| **6.1.2 초점 이동과 표시** | 키보드 초점은 논리적으로 이동하고 **시각적으로 구별**되어야 한다 |
| **6.1.3 조작 가능** | 대각선 길이 **6.0mm 이상** 권장, 컨트롤 테두리 안쪽 1px 이상 여백 |

**KWCAG 2.2 에는 WCAG 1.4.11(Non-text Contrast)에 해당하는 검사항목이 없다.** UI 컴포넌트 경계·그래픽 객체의 대비 요구가 부재한다.

### 이 사실이 바꾼 판단 두 가지

**① 보더 토큰의 근거를 정정했다.** 처음에는 "떠 있는 면이 1.4.11 미달"이라고 봤으나 두 가지가 틀렸다 — KWCAG 에는 해당 조항이 아예 없고, WCAG 1.4.11 도 원문이 *"user interface components 를 **식별**하는 데 필요한 시각 정보"* 라서 모달·카드 **컨테이너 면** 자체는 대상으로 보기 어렵다. 따라서 보더는 **규정 준수가 아니라 다크에서 경계를 잃지 않기 위한 실무적 선택**이다.

**② 면끼리 3:1 은 애초에 불가능하다.** 라이트에서 흰 면과 3:1 이 되려면 상대 면이 `gray.600`(`#595B61`) 수준이어야 하고, 다크 모달이 dim 위에서 3:1 이 되려면 `gray.500`(`#989BA1`) 이상이어야 한다. 둘 다 그 테마를 포기하는 값이다. **면은 지각 힌트, 경계는 보더** 로 역할을 나눈다.

### 큰 텍스트 예외는 쓰지 않는다 (보수적 적용)

두 기준 모두 큰 텍스트에 3:1 을 허용하고 기준선도 같다(18pt=24px, 14pt bold=18.67px). 우리 타이포 27개 중 **7개**(display 2 · heading 4 · title-lg-strong)가 해당한다.

그러나 **색 토큰이 어느 크기와 조합될지 정의가 없으므로 예외를 적용하지 않는다.** 전 색상에 4.5:1 을 적용하고, 미달이 났을 때만 "큰 텍스트로 쓰면 구제 가능"을 참고 정보로 표시한다. 기준보다 엄격한 쪽이며 의도적이다.

## 4-2. 텍스트 검사 면을 4개로 넓혔다

이전에는 `bg.normal` 위에서만 검사해 **카드·모달 위의 텍스트가 사각지대였다.** `normal` · `normalAlternative` · `elevated` · `elevatedAlternative` 4개 면 전부로 넓히자 검사가 50건 → **158건**이 되고 미달 3건이 드러났다.

| 테마 | 토큰 | 면 | 대비 |
|---|---|---|---|
| 라이트 | `label.alternative` | `bg.normalAlternative` | 4.42 |
| 라이트 | `label.alternative` | `bg.elevatedAlternative` | 4.42 |
| 다크 | `label.alternative` | `bg.elevated` | 4.35 |

**알파만 올려 해결했다** — 라이트 `gray.700 @69% → @70%`(최저 4.55), 다크 `gray.400 @70% → @74%`(최저 4.71). base 색은 그대로이고 새 토큰도 필요 없었다. 기존의 라이트 69 / 다크 70 이라는 근거 없는 비대칭도 함께 정리됐다.

> `opacity.69` 는 이 변경으로 미참조가 됐다. 원본 14단계에 속하므로 삭제하지 않고 남긴다.

## 4-3. 포커스 토큰 — 컴포넌트 없이 정할 수 있는 만큼만

KWCAG 「6.1.2 초점 이동과 표시」가 *"초점을 받은 콘텐츠는 시각적으로 구별되어야 한다"* 를 요구하는데 **링 색 토큰이 없었다.** `preview.html` 도 임시로 `--color-accent-fg-blue` 를 쓰고 있었다.

컴포넌트가 없어 링의 모양·위치는 정할 수 없지만 **색과 두께는 지금 정할 수 있어** 세 개만 만들었다.

| 토큰 | 값 | CSS 변수 |
|---|---|---|
| `color.interaction.focus` | 라이트 `{color.blue.600}` · 다크 `{color.blue.400}` | `--color-interaction-focus` |
| `focusRing.width` | 2px | `--focus-ring-width` |
| `focusRing.offset` | 2px | `--focus-ring-offset` |

색은 **라이트 600 / 다크 400** 규칙을 그대로 따른다. 4개 면 전부에서 3:1 을 넘는다(라이트 최저 4.79, 다크 최저 5.02).

### 링은 반드시 띄워야 한다

컴포넌트 면 위에 직접 그리면 대비가 무너진다.

| 링을 얹는 대상 | 라이트 | 다크 |
|---|---|---|
| 페이지 배경 (offset 있음) | 4.79~5.13 ✓ | 5.02~6.03 ✓ |
| `primary.normal` | 2.61 ✗ | 2.99 ✗ |
| `accent.bg.violet` | **1.00** ✗ | 1.60 ✗ |

`accent.bg.violet` 은 링 색과 **완전히 같은 색**이 되어 사라진다. 그래서 `focusRing.offset` 이 선택이 아니라 필수다. 이 사실을 `CLAUDE.md` 접근성 항목에도 적었다.

두 겹 링(안쪽은 표면 색, 바깥은 포커스 색)이 더 안전하지만, **그 조합은 컴포넌트 레벨의 구성이라 토큰으로 만들지 않았다.** 의미 단위 elevation 토큰(미결 3번 계열)과 함께 다룰 문제다.

### 지금 정할 수 없는 것

- **조작 영역 크기** — KWCAG 6.1.3 은 **6.0mm 이상**(물리 크기), WCAG 2.5.8 은 **24×24 CSS px**. 단위가 달라 각각 확인해야 하고 둘 다 컴포넌트 치수 문제다.
- **2.4.11 Focus Not Obscured** — 스티키 헤더 등이 포커스된 요소를 가리는지, 레이아웃 문제다.
